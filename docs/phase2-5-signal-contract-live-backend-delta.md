### 3.2 `SignalCandidate`

The contract's `SignalCandidate` is **adapter-owned**. No Daniel-side counterpart. Every field is the adapter's responsibility. The contract is internally consistent. No delta against Daniel.

The dedupe `raw_source_ref` six-field identity (`source, symbol, strategy_id, model_version, predicted_at, side`) is consistent with the contract but **cannot be built from `live_signals` alone** — `strategy_id` and `model_version` require joins. See GAP-REC-001 in the gap register.

### 3.3 `RecommendationProjection`

Frontend-side projection; no Daniel-side counterpart. The contract is internally consistent.

The mapping `position +1 → open_long`, `position -1 → open_short`, `position 0 → hold` (or "no projection emitted") is the load-bearing translation. The contract §3 enum is `open_long \| open_short \| close_long \| close_short \| hold` — but Daniel's signal doesn't distinguish "open" from "close" because Daniel doesn't know the per-account current position. The adapter must consult per-account state (which comes from the future `account-intent-builder`) to decide `open` vs `close`.

**Implication:** the contract's `recommendation_type` enum requires per-account context the adapter doesn't have today.

### 3.4 `EligibilityCheck`, `ExecutionPolicyDecision`, `BrokerSubmission`, `ExceptionReview`, `RecordArtifact`

All BFF / adapter / future Daniel responsibility. No delta against `live-components-main` because none of these objects exist on the Daniel side.

## 8. Net deltas — actionable items

### 8.1 Contract should be corrected (small edits)

The original contract should receive a follow-up commit (not in this audit) to fix:

1. **§2 verbal description**: replace `buy \| sell \| hold \| exit` with `open_long / open_short / hold` to match the §3 enum.
2. **§3 `DanielSignalRaw.signal`**: change `-1 \| 1` to `-1 \| 0 \| 1` (Daniel emits 0 too).
3. **§3 `DanielSignalRaw.predicted_at`**: clarify that the wire shape is `int` (UNIX seconds) and the adapter parses to ISO-8601. Currently typed as `string` (ISO-8601) which understates the conversion.
4. **§3 `DanielSignalRaw.last_prediction_ts`**: same shape conversion clarification.
5. **§3 `DanielSignalRaw.source_collection`**: tighten to `"live_signals"` only. The other collections are upstream features, not adapter intake sources.
6. **§3 `DanielSignalRaw.model_version`**: confirm it is NOT on the wire; adapter derives from GCS path or a separate registry write. Mark as **derived** rather than `TODO`.
7. **§3 `DanielSignalRaw.strategy_id`**: confirm it is NOT on the wire; adapter derives via `available_strategies.collection`. Mark as **derived**.
8. **§3 `DanielSignalRaw.confidence_score` and `sharpe_metric`**: define an aggregation rule (or drop). The `rl_predictions` Q-values and the `sharpe_series` multi-dimensional output are not a single scalar.
9. **§3 `RecommendationProjection.recommendation_type`**: document that the `open` vs `close` decision requires per-account current-position context, which comes from the future `account-intent-builder`, not from the signal itself.
10. **§4 mapping rows**: incorporate the shape conversions from items 3-4 above.

### 8.2 Contract is correct; backend gap remains

### 8.4 Frontend surfaces that must change as a result

The current frontend `RecommendationProjection`-consuming surfaces (recommendation detail, exceptions queue, dashboard) consume the BFF-projected shape. **No frontend surface needs to change today** — the adapter sits between the BFF and the frontend, not between the BFF and the surfaces.

The future change at the frontend level: when `model_version` and `strategy_id` are surfaced in the recommendation detail's "Why this recommendation" lineage panel, those values must come from the adapter's derivation, not from the wire. This is a future Phase 3+ concern, not a Phase 2.5 concern.
