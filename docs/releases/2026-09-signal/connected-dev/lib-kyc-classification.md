# `apps/web/src/lib/kyc/` classification — audit 2026-09-10 (no refactor performed)

Founder review 2026-09-10: audit only; do not refactor, rename or re-home KYC
code into Alpaca onboarding code. Classes: **A** demo/mock only · **B**
historical unused code · **C** connected runtime dependency · **D** generic
frontend gate with no provider semantics.

Facts that apply to every row: no vendor SDK, secret, env or name exists
(contract assertion `VENDOR_NAMES`); `REFI_KYC_MOCK_CONTROLS` is forced to `0`
on a connected deployment (env invariant, boot failure otherwise);
`REFI_KYC_PROVIDER` defaults to `unconfigured` and is **not** forced by the
connected invariant (finding F-1 below); the attestation mapping refuses any
`source: "mock"` provenance (`KYC_EVIDENCE_MOCK`) and any untrusted provenance,
so mock evidence can never satisfy the attestation/admission gate in any mode.

## Findings

- **F-1 (hardening candidate, not performed):** the connected-deployment
  invariant forces `REFI_KYC_MOCK_CONTROLS=0` but not
  `REFI_KYC_PROVIDER=unconfigured`. With `mock` set on a connected deployment the
  mock session can be _started_ (it can never advance without controls, and its
  evidence is refused at attestation), so the only effect is a misleading
  "Verification in progress" display. Recommend adding the invariant when the
  next code slice is approved.
- **F-2:** no `lib/kyc` code is Alpaca-specific and none should be renamed to
  imply Alpaca onboarding authority; the generic lifecycle is retained as-is
  pending Daniel A1/K1.
- **F-3:** the demo tier's mock KYC behaviour (persona flow, `demo-tier.spec.ts`,
  `kyc.spec.ts`) stays inside the demo boundary; nothing in it can satisfy a
  connected gate (env invariant + provenance refusal + release policy).
