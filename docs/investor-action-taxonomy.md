# Investor Action Taxonomy

**Date:** 2026-05-20
**Purpose:** The canonical, enforceable catalog of every action a Managed-mode or Signal-mode investor can take. Anything not listed here is a category error.

---

## How to use this doc

- Frontend code: `InvestorActionName` is a TypeScript string-literal union exported from `apps/web/lib/sec203a/actions.ts`. Any code that constructs an action outside this union must fail type-check.
- BFF code: every state-changing route names its action; the receipt logged into `InvestorActionReceipt` carries the action name verbatim.
- Tests: a Playwright tripwire iterates every interactive control on every investor screen and asserts its action (if any) is in this catalog.

If a new action is proposed: do not add it here unilaterally. Take it to Zeshan + Counsel; once approved, update this doc, the union type, and the catalog rows in the order listed.

---

## Naming canon

Final renames adopted on 2026-05-20 review:

- `activateManagedPolicy` → **`activateExecutionPolicy`** (the investor-approved object is the Execution Policy; activation produces a new signed version)
- `pauseAutomation` → **`pauseManaged`** / `resumeAutomation` → **`resumeManaged`** (mutate ManagedExecutionState only; the active execution policy version is unchanged)
- `approveUserSideException` → **`resolveException`** (single action; resolution category in payload, constrained to `ExceptionResolution`)
- `viewRecord` / `downloadRecord` / `exportRecord` are NOT investor actions — they are `RecordAccessAction`s and emit `RecordAccessLog`, not `InvestorActionReceipt`.

## Record-access actions (separate stream)

These are NOT investor actions. They emit `RecordAccessLog`, not `InvestorActionReceipt`. The two streams are independent by design.

| Action           | Trigger surface                                                                 | Notes                                 |
| ---------------- | ------------------------------------------------------------------------------- | ------------------------------------- |
| `viewRecord`     | `GET /api/v1/investor/records/[id]`, `GET /api/v1/investor/orders/[id]/lineage` | Logged for compliance access auditing |
| `downloadRecord` | future `/records/[id]/download`                                                 | Logged with format                    |
| `exportRecord`   | future `/records/export`                                                        | Logged with export_job_id             |
| `viewEvidence`   | `GET /api/v1/investor/evidence/{internet-adviser,multi-client,outages}`         | Examiner-facing evidence reads        |

## Prohibited actions (must never appear in code, UI, or copy)

| Forbidden action                                                                                                  | Why it's forbidden                                                                                                                     | If you encounter it                                                                                                                         |
| ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `acceptRecommendation`                                                                                            | Routes per-trade approval through a human-style action; contradicts software-generated advice + managed execution authorization model. | Delete the control; replace with action #1 (program-level activation) for activation flows, or no control at all for normal Managed advice. |
| `approveTrade` / `approveRebalance`                                                                               | Same as above.                                                                                                                         | Same as above.                                                                                                                              |
| `adminRebalance` (e.g. mapping to `template.admin action=rebalance`)                                              | Admin operational command; incompatible with investor authorization model.                                                             | Hard fail in code review. Delete the path.                                                                                                  |
| `manualTradeSubmit`                                                                                               | Bypasses backend lifecycle; creates frontend-invented order state.                                                                     | Delete.                                                                                                                                     |
| `forceInference`, `forceTraining`, `cancelOrder`, `rollback`, `configWrite`, `controlsWrite`, `accountInitialize` | Admin-only; live in Daniel's admin-portal and must never reach investor UI.                                                            | Delete the path. Verify CI tripwire (G-012).                                                                                                |
| `staffReviewAdvice`, `founderApproveRecommendation`, `editRecommendation`                                         | Human-authored advice; direct Rule 203A‑2(e) violation.                                                                                | Delete. ## Mapping rules

- An investor action **maps to exactly one** outcome category: state mutation, blocked-state acknowledgment, or record view.
- An investor action **never** maps to an admin command. The complete admin command set lives in Daniel's `apps/admin-portal/backend/api/{accounts,operations,settings,internal}.py` and is enumerated in `admin-investor-boundary.md`.
- Where Managed-mode operations require server-side intervention (e.g. system pause on stale broker), the operation is **system-initiated, not investor-initiated** — it does not become an action in this catalog.

## Test implication

- `apps/web/lib/sec203a/actions.ts` exports:
  ```ts
  export const InvestorActions = ["activateManagedPolicy", "pauseAutomation", ...] as const;
  export type InvestorActionName = typeof InvestorActions[number];
  ```
- Every BFF state-changing route accepts an `action: InvestorActionName` parameter that must match the catalog row.
- Vitest unit test: every entry in `InvestorActions` appears in this doc's catalog table (parse the markdown row count vs the union length).
- Playwright tripwire: iterate every interactive `[data-action]` on every investor route, assert value ∈ `InvestorActions`.
- Copy-scanner: add the forbidden action strings ("accept recommendation", "approve trade", "approve rebalance", "force inference", "manual rebalance", etc.) to `blocked-terms.ts` if not already.
