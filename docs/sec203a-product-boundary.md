# SEC 203A‑2(e) Product Boundary

**Date:** 2026-05-20
**Purpose:** Encode the SEC Rule 203A‑2(e) Internet Adviser posture as enforceable product rules. This is the control layer — every screen, action, copy line, and test must conform.

---

## What this product is

A software-based digital investment adviser. The user experience surfaces:
eligibility · digital advisory relationship · client profile · broker connection · account preferences · strategy / portfolio policy · managed execution settings · software-generated recommendation or rebalance state · risk and compliance status · execution status · records and audit trail · support boundary.

## What this product is not

- A trade approval app.
- A human-adviser workflow.
- A discretionary human portfolio manager.
- A broker replacement.
- A custody platform.
- A loose signal feed with unmanaged execution.
- A model marketplace.
- A trading bot.

---

## The seven enforceable conditions of Rule 203A‑2(e)

| #   | Condition (paraphrased)                                                                                  | Where the product proves it                                                                                           |
| --- | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 1   | Operational, interactive website/app                                                                     | `apps/web` deployed; uptime telemetry; investor self-serve flow end-to-end                                            |
| 2   | Digital advisory service on ongoing basis to >1 client                                                   | Lifecycle state + active-client counter in `InvestorLifecycleState`; alert if active < 2                              |
| 3   | Client-specific advice generated by software-based models                                                | Every `AdvisoryRecordProjection` references a model artifact + intent_id from Daniel's chain                          |
| 4   | Software uses personal information supplied by each client through the platform                          | `InvestorProfileSnapshot` version pinned on every advisory record; profile capture only via `/us/onboarding/profile`  |
| 5   | Advice delivered exclusively through the operational interactive platform                                | All advice rendered in `/us/app/*`; no email/SMS/PDF advice channels; receipts log `delivery_channel: "platform"`     |
| 6   | Staff do not generate / edit / approve / expand / supplement client-specific advice outside the platform | Support boundary classifier (`/us/app/support`); blocked-terms scanner; admin-investor boundary doc; tripwire CI test |
| 7   | Records exist                                                                                            | `InvestorActionReceipt` + `AdvisoryRecordProjection` + ack history surfaced in `/us/app/records`                      |

A breach of any one of these is a P0 product defect.

## Prohibited user actions

- `acceptRecommendation`, `approveTrade`, `approveRebalance` — per-trade investor approval is incompatible with software-generated advice + managed execution.
- `adminRebalance`, `manualTradeSubmit`, `forceInference`, `cancelOrder`, `rollback` — all admin/operator commands.
- `staffReviewAdvice`, `founderApproveRecommendation`, `editRecommendation` — would create human-authored advice.

## Backend source of truth

- Daniel's execution lifecycle (DDL + Pub/Sub) is the system of record for trading. Frontend never invents lifecycle state.
- Frontend BFF projects backend state into investor-readable shapes per `bff-prototype-state-contract.md`.
- Missing backend tables for product state (profile, disclosure registry, lifecycle, auth link) are handled via Bucket B prototype storage with explicit non-SoR labeling.

## Temporary BFF-owned state

See `bff-prototype-state-contract.md`. Investor-product flows are testable end-to-end on prototype state today; final authority migrates upstream when Daniel ships.

## Record requirement

- Every state-changing investor action emits an `InvestorActionReceipt`.
- Every advisory-state event projects to `AdvisoryRecordProjection` with version pins (profile, prefs, disclosures, model).
- Records are exportable from `/us/app/records` in machine-readable form.
- Five-year retention is upstream (G-117/118) and out of frontend scope; the frontend ensures shape and accessibility.

## UI implication

- Every screen must define five states: loading, empty, blocked, error, success.
- Every blocked state must explain reason, user action, system action, record location.
- Every action button must be traceable to a row in the allowed-actions table.
- Every advisory display must link to its underlying record.
- Plain language; no admin jargon; no per-trade approve language anywhere.

## Test implication

- **Vitest:** allowed-action taxonomy enforced as a runtime + type-level union; any code constructing a non-allowed action fails type-check.
- **Vitest:** every BFF state-changing route asserted to emit a receipt.
- **Vitest:** copy-scanner (`scripts/scan-copy.ts`) blocks prohibited phrases — already in place; extend with this doc's terms.
- **Playwright:** Managed-mode flow proves no Accept-Recommendation button is reachable.
- **Playwright:** admin paths are unreachable from any investor route (404 / not-found).
- **Playwright:** every screen renders its loading / empty / blocked / error / success states.
- **CI tripwire (G-012):** investor BFF cannot import or proxy to admin endpoints.
- **a11y (G-116):** axe-core on every primary investor route, no serious/critical violations.
