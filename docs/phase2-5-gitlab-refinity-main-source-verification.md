## 2. Repo identity conclusion

**The GitLab repo `refinity_dev/refinity-main` is the canonical Daniel backend monorepo.** It is **a newer and broader version** than the local `live-components-main` folder.

Specifically:

- **`live-components-main` ≠ canonical.** It contains only the **`inference-worker`-equivalent Python pipeline** (renamed/restructured under `apps/inference-worker/src/component_a..e`) plus the **`portfolio-analyzer-web`** FastAPI Cloud Run service. Both also exist in the GitLab repo as service-level apps.
- **The local snapshot was a partial export.** The local `live-components-main.zip` was likely produced for the Phase 2 reconciliation exercise and never reflected the full monorepo. Recent GitLab commits (`portfolio-manager bug fixes`, `admin-portal wiring`, `multi-stream convention`, `trade-manager, exec-gateway and admin-portal hardening`) show active development of the services the prior audit considered "planned but not implemented."

## 4. Contract impact

### Does `docs/phase2-5-signal-to-investor-product-contract.md` still match the GitLab repo?

**No, not fully.** Three classes of impact:

1. **Wire-shape divergence** (covered in detail in `phase2-5-gitlab-contract-delta.md`):
   - `position` → `signal`
   - `date: int` → `ts_utc: datetime`
   - `symbol` → `asset_id`
   - Add `stream_id`, `strategy_source`, `label`, `proba`
   - Multi-stream identity (`(stream_id, ts_utc)` not `(symbol, date)`)
   - `model_version` is on the wire, not derived
   - `strategy_id` is encoded in `stream_id`, no separate derivation

2. **"Missing services" reversal**: the prior audit's `phase2-5-daniel-to-refi-alignment-gap-register.md` rows that named `account-intent-builder`, `risk-engine`, `exec-gateway`, `trade-manager`, `template.admin action=rebalance target_account_id=X` as **"missing on Daniel side"** should be reclassified as **"implemented on Daniel side; mapping work pending on BFF"**. The boundary architecture the contract codifies is still correct; the gap between frontend simulation and backend reality is narrower than the prior audit concluded.

3. **Skeleton residual**: `audit-writer` and `compliance-adapter` remain skeletons. The SEC 203A-2(e) record-retention and pre-trade-compliance gates still require Daniel-side production work.

### Additional corrections needed

- Add `stream_id`, `strategy_source`, `label`, `proba` as wire fields on `DanielSignalRaw`.
- Replace `symbol` with `asset_id` (the frontend's `symbol` is the broker-tradable ticker, which equals `asset_id` here — confirm by reading `apps/inference-worker/src/orchestrator/orchestrator.py` for the actual signal-publish path; deferred).
- Multi-stream identity: same `account_id, asset_id, ts_utc` triple can carry both `"AAPL~rf"` and `"AAPL~rl"` rows; the adapter must define a stream-selection rule (likely "prefer strategy_source per investor's policy" or "treat as independent signals").

### Does `position: 0` still exist?

**Uncertain.** The inspected `inference-worker` tests publish `signal` values of `1` and `-1`; the `0` (flat) case is not present in the tests I inspected. The `0` case existed in the local `Inference Pipeline/generate_final_signal.py:170-173` (`raw_signals.ffill().fillna(0)`). Whether the GitLab `inference-worker/orchestrator` preserves the `0` step requires a deeper code read of `apps/inference-worker/src/orchestrator/`. Deferred.

### Is `live_signals` still the principal adapter intake?

**No.** The adapter intake source is now the Spanner `signals` table (read via the inference-worker's Spanner client or via a downstream service that already filters). MongoDB `live_signals` may still exist as a legacy mirror; deferred.

### Does GitLab add account-level recommendation semantics?

**Yes — fully.** The `account.intent.ready` and `risk.approved` events carry `account_id` + `intent_id` + `partition_key`. The frontend's `RecommendationProjection.recommendation_id` and `account_id` align at the field level.

### Does GitLab add execution semantics?

**Yes — fully.** `orders.cmd` from `exec-gateway` and `orders.evt` from `trade-manager` carry `plan_id`, `client_order_id`, `account_id`, `status`, `ts`. Aligns with frontend `Order`, `OrderEvent`, `BrokerOrderAttempt`, `Fill` schemas.

### Does GitLab add a broker path?

**Yes.** `trade-manager` (16 Python files) handles broker submission. `risk-engine` README mentions SnapTrade integration for position refresh. Broker is a real integration, not a stub.

### Does GitLab add audit records?

**Partially.** The `audit.evt` Pub/Sub topic and `apps/audit-writer/` service skeleton exist, but `audit-writer` has 0 Python files. The trade-lifecycle Spanner tables (`OrderEvents`, `BrokerOrderAttempts`, `BrokerInteractionsLog`, etc.) are the durable execution-record system. Investor-side records (`InvestorActionReceipt`, `RecordAccessLog`) remain BFF-owned.
