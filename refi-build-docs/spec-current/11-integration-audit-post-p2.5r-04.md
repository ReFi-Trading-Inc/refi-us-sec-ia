## 1. Headline finding

The P2.5R-04 preview slice (`packages/api-clients/src/mocks/handlers.bff.ts`, `hooks/bff.ts`, three new BFF endpoints, persona lineage fixtures) is **structurally sound and safe to build the lineage UI ticket (P2.5R-05) on**. Persona correlation IDs thread end-to-end through Maya's chain; Sarah's exception chain is consistent. **However**, this audit found 11 real wire-shape and topic-naming drifts against Daniel's actual code — most non-blocking individually, but cumulatively they will produce silent contract failures at first cutover unless fixed before P2.5R-05 ships. The most consequential are: (a) **Pub/Sub topic naming is wrong** (proposed `client.*` topics don't match Daniel's `dev-*` prefix convention; we will get IAM-denied at publish time), (b) **`OrderEvent` type uses `prev_status/new_status` while Daniel's table uses `from_status/to_status` and includes `event_type` as a separate columnar field, not in the event_id**, (c) **`TradingControlState` enum is misaligned** with `apps/common/trade_lifecycle/states.py CONTROL_MODES` (frontend says `"halt"`, Daniel says `"halt_all"|"halt_new_orders"`), (d) **`BrokerPosition.notional` does not exist in `Positions` DDL** — column is `market_value`, and Positions is keyed by `(account_id, asset)` with no `symbol` or `side` columns. These will all silently break the first real Spanner read.

The reframe itself (tier-aware UI, removal of per-rec Accept) is **correctly executed** in the recommendation detail page and the dashboard; no SEC Rule 203A-2(e) regressions found. Persona Sarah has one notable inconsistency (active ExecutionPolicy with `kyc=false`) that should be reconciled before P2.5R-17 lands.

## 5. Pub/Sub topic naming clarification (§2, §10)

**Daniel's actual conventions** (verified against `contracts/fixtures/*.json` and `docs/architecture/topics_subs_dlqs.txt`):

- All non-prod topics carry `dev-` prefix.
- All topic names use **dot notation**: `dev-account.intent.ready`, `dev-risk.approved`, `dev-orders.cmd`, `dev-orders.evt`, `dev-audit.evt`, `dev-template.admin`, `dev-account.admin`, `dev-template.rebalance.intent`.
- Every topic has a corresponding `.dlq` sibling.
- The convention is `<env>-<aggregate>.<verb-or-noun>[.dlq]`.

**Our proposed names are wrong against this convention:**

| `client.exception.approve`         | `dev-client.exception.approve`                                                                |
| `client.exception.reject`          | `dev-client.exception.reject`                                                                 |
| `support.event` (10 §5)            | `dev-support.event`                                                                           |

**Note:** in the 5-command model from `09 §1 Q5`, items 2–4 are mislabeled:

- "`system.account_intent.generated`" should map to **`dev-account.intent.ready`** (already exists; payload per `account.intent.ready.json` fixture).
- "`system.account_intent.approved_by_policy`" should map to **`dev-risk.approved`** (already exists).
- "`system.execution_plan.submit`" should map to **`dev-orders.cmd`** (already exists).

The 09 doc presents these as if they need new topics, but they are net-existing Daniel topics that the BFF should **subscribe to / read from `UiEventTimeline`** (since `UiEventTimeline` per DDL is the projection of audit events into Spanner — that table at `spanner_ddl_all.txt` is the BFF's actual read path for system events, not a Pub/Sub subscription).

**Required fix:** rewrite §1 Q5 of `09` and `06 §3` to use Daniel's actual topic names. Distinguish: BFF **subscribes** to `dev-orders.evt` (via `UiEventTimeline` projection) and **publishes** new `dev-client.*` topics.

Since `refi-api.yaml` (1,960 lines) now declares only `/api/v1/*` paths but the codebase calls legacy `/v1/*` paths, the generated types in `api.ts` are produced from the YAML's BFF surface — yet the runtime calls (`useOrders` → `/orders`) target paths NOT in the YAML. **The BFF surface is documented, the legacy surface is undocumented.** A consumer hitting `useOrders()` against a future live BFF will 404.
